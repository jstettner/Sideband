# Sideband protocol

The contract between the pieces of Sideband. The watch app talks only to this, so you can
write your own backend (or runner, or client) against it.

| File | What |
| --- | --- |
| `openapi.json` | HTTP API, client ↔ backend. Generated from `src/Api.ts` |
| `runner.md` | WebSocket protocol, backend relay ↔ runner |
| `examples/` | Sample payloads. Every file is decoded against its schema in `test/` |
| `src/` | Effect Schemas and the `HttpApi` definition, shared by our backend and runner |

`src/` is the source of truth. After changing it run `bun run gen` and commit `openapi.json`;
`bun run check` fails if they've drifted.

## HTTP API

All endpoints require `Authorization: Bearer <token>`. Bodies are JSON unless noted.

```text
POST /v1/turn?session=main                submit a turn (audio or text)
GET  /v1/turns/{idempotency_key}           outcome of a turn
GET  /v1/status?session=main               agent + session state, for widgets
POST /v1/sessions/{session}/new            fresh agent session behind this name
POST /v1/sessions/{session}/compact        compact the agent session
```

### Submitting a turn

```sh
# audio: the raw recording is the body
curl -X POST "$BACKEND/v1/turn" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: audio/mp4" \
  --data-binary @command.m4a

# text: the client already transcribed
curl -X POST "$BACKEND/v1/turn" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"text": "Did the production deploy finish?"}'
```

- Audio: `audio/mp4` (AAC in MP4/M4A) is required; a backend may accept more formats and
  replies `415 unsupported_media_type` otherwise. Max 1 MB (~4 minutes at 32 kbps), else
  `413 payload_too_large`. Mono 16 kHz at 24-32 kbps is plenty for speech.
- `session` is a stable name you choose (default `main`). The agent's own session IDs change
  over time (new session, compaction) and are never exposed.

### Turn outcomes

`POST /v1/turn` and `GET /v1/turns/{key}` return the same `TurnState`, discriminated by `status`:

| `status` | HTTP | Meaning |
| --- | --- | --- |
| `completed` | 200 | `watch_text` to display; optional `speak_text`, `full_text`, `context` |
| `running` | 202 | Still in flight. Poll `GET /v1/turns/{key}` after `retry_after_ms` |
| `needs_approval` | 200 | The agent paused for an approval the client can't give yet |
| `failed` | 200 | The agent ran it and it failed (`agent_failed`) or was cut short (`interrupted`) |
| `unknown` | 200 | Contact with the agent was lost; it may or may not have run. Never re-sent |

A backend holds `POST /v1/turn` open while the agent works (ours: up to ~25 s) before
answering `running`, so clients should allow at least 35 s before timing out.

### Idempotency

Every `POST /v1/turn` carries an `Idempotency-Key` header: 16-128 characters of
`[A-Za-z0-9_-]`, generated by the client before the first attempt (a UUID). Agents may take
actions, so a turn must never run twice:

- Retrying the same recorded command reuses the same key.
- Same key, same payload, turn finished: the stored outcome is returned again.
- Same key, same payload, turn in flight: `running`.
- Same key, different payload: `422 idempotency_conflict`.
- Keys are kept for at least 24 hours.

A backend must not queue turns: if the agent is unreachable it answers `503 agent_offline`
without running anything, rather than running the command later by surprise.

### Errors

A request that was refused (no turn was created) gets a non-2xx status and:

```json
{ "error": "agent_offline", "message": "The agent is offline. Nothing was run.", "retryable": true }
```

| `error` | HTTP | `retryable` |
| --- | --- | --- |
| `invalid_request` | 400 | false |
| `unauthorized` | 401 | false |
| `not_found` | 404 | false |
| `session_busy` | 409 | true |
| `payload_too_large` | 413 | false |
| `unsupported_media_type` | 415 | false |
| `idempotency_conflict` | 422 | false |
| `internal_error` | 500 | true |
| `not_supported` | 501 | false |
| `transcription_failed` | 502 | true |
| `agent_offline` | 503 | true |

`retryable: true` means retrying the same request (same key) is safe and may succeed.

### Compatibility

`/v1` only changes additively. Clients ignore fields they don't know, and treat an unknown
`status` or `error` code as a generic non-retryable failure.
